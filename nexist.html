EXPERIMENTAL RESEARCH / NX DATA MODEL / PROJECT 007

NEXIST.

A model for describing digital entities that are defined as possibilities before they are explicitly realised. NEXIST explores how identity, requirements, relationships, and lifecycle history can be represented together in one structured NX Unit.

TRY THE NX PLAYGROUND ↘ EXPLORE THE MODEL
01 / THE IDEA

What is NEXIST?

NEXIST is an experimental data-model and Python core-engine project. Its central record is an NX Unit: a structured representation with its own identity, type, attributes, requirements, relationships, lifecycle state, and event history. A unit can be described and evaluated without claiming that the thing it represents already exists outside the model.

01 / IDENTITY

Describe a possibility

Give an NX Unit a unique ID, a label, a type, and structured attributes.

02 / CONDITIONS

Check requirements

Declare conditions and evaluate them against a supplied facts snapshot.

03 / LIFECYCLE

Record its state

Track whether a unit is potential, eligible, realised, or archived.

Important: NEXIST is a research prototype, not a proven new fundamental computing primitive. Similar ideas exist in object models, graphs, constraint systems, and knowledge representation. Its novelty and practical advantage still need comparative research and testing.
02 / LIFECYCLE

How an NX Unit changes

Passing requirements does not automatically realise a unit. Evaluation and realisation are separate operations, so the transition is deliberate and recorded.

STATE 01POTENTIAL

The unit is defined, but its requirements have not been confirmed.

STATE 02ELIGIBLE

The supplied facts satisfy all declared requirements.

STATE 03REALIZED

An explicit action records that the unit has been realised in the model.

STATE 04ARCHIVED

The unit is inactive, while its record and history are retained.

04 / CORE MODEL

What an NX Unit contains

The Python prototype uses the same conceptual building blocks. Requirements are declarative; the engine compares values rather than executing arbitrary Python code from a requirement.

NXUnit
 ├─ id              unique identity
 ├─ label, kind     meaning and category
 ├─ attributes      descriptive data
 ├─ requirements    conditions to evaluate
 ├─ relations       links to other NX Units
 ├─ parent_ids      composition lineage
 ├─ state           POTENTIAL / ELIGIBLE / REALIZED / ARCHIVED
 └─ events          recorded lifecycle history

05 / RESEARCH DIRECTION

What must be proven next?

The next stage is not to claim that NEXIST is unprecedented. It is to test whether the combined model provides a measurable benefit over ordinary Python data classes, graph structures, and constraint evaluation.

PHASE A

Formal specification

Define invariants, state transitions, composition rules, and error behaviour precisely.

PHASE B

Comparative benchmarks

Compare correctness, clarity, performance, and complexity against established approaches.

PHASE C

Demonstrate a use case

Find a problem where the NX model offers a useful capability that is difficult to express cleanly otherwise.

Scope boundary: “Realised” means explicitly recorded as a state inside NEXIST. It does not mean that a physical object, service, or real-world event has automatically been created.
